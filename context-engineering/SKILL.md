# 上下文工程

给 AI（和新同事）的上下文要**当资产管理**：结构化、随代码走、定期防腐——「都在老员工脑子里」的项目上下文不可复用也不可审计。

## 四件套

| 文档 | 回答什么 | 腐化信号 |
|---|---|---|
| 产品上下文 | 做什么、为谁、不做什么 | 还写着已砍掉的功能 |
| 技术栈上下文 | 用什么、为什么、版本约束 | 版本落后现实一个大版本 |
| 工作流上下文 | 怎么做：分支/测试/发布流程 | 和 CI 实际配置矛盾 |
| 任务轨道 | 现在做到哪：进行中工作单元 | 堆着三个月前未归档的轨道 |

新项目从零写四件套；接手老项目先**从代码库反推**出四件套再动手改代码——反推的文档标「待验证」逐步校正。

## 纪律

- **动手前先读上下文**；实现选择引用上下文依据（「按技术栈上下文 §数据库」）——决策可追溯。
- 小步更新：上下文改动随对应代码一起提交、一起 review——**文档和代码不同步就双双作废**。
- 感觉不对就查证：发现文档与现实矛盾，当场修——「感觉 stale」是最准的腐化探测器。
- 每项内容必须**可指导行动**（能影响一个决策或行为）——不满足的删掉，上下文不是许愿池。
- 重大变更通知团队；历史演进靠 git 追，不靠口头。

## 收尾清单

四件套齐 / 随代码提交 review / 动手前先读 / 引用有出处 / 矛盾当场修 / 内容可指导行动 / 轨道定期归档。

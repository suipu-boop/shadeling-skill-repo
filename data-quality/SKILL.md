# 数据质量

数据质量事故比代码 bug 贵：坏数据**悄悄污染下游所有决策**。体系建设四步：定维度 → 建测试 → 立合同 → 上监控。

## 六个质量维度（检查表）

| 维度 | 查什么 | 例子 |
|---|---|---|
| 完整性 | 不缺 | 关键列非空、行数无骤降 |
| 唯一性 | 不重 | 主键/业务键唯一 |
| 有效性 | 合法 | 值在枚举/范围内、格式合规 |
| 准确性 | 属实 | 与外部事实源交叉核对 |
| 一致性 | 不矛盾 | 跨表/跨系统对得上（A 表总额 = B 表求和） |
| 时效性 | 够新 | 数据新鲜度（最后更新时间）在 SLA 内 |

## 数据测试金字塔

```
        集成测试（跨表关系：外键、汇总一致性）
       单元测试（单列/单表：非空、唯一、范围）
      结构测试（schema：列存在、类型、不漂移）
```

- **结构测试打底**：schema 变更是最常见的静默破坏源（上游改了列名，下游全断）——结构漂移必须第一时间报警。
- 关键列优先：别试图全测——**测关键的 20% 列**（金额、ID、状态、时间戳），覆盖率虚高没意义。
- 关系测试：孤儿外键（引用不存在的客户）是数仓慢性病，集成层抓。

## 数据合同（下游契约）

- 表的 schema、语义、新鲜度 SLA、变更流程**写成显式合同**——上游想改结构走评审，不是直接改。
- 变更通知机制：破坏性变更提前通知下游，版本化过渡——「上游一个 rename，下游三个报表挂」靠合同防。
- 合同进版本库，与代码同评审纪律。

## 监控与告警

- **新鲜度监控**：每张关键表的最后更新时间，超过 SLA 报警——「没人发现数据三天没更新」是最常见事故。
- 检查失败即阻断：质量不过关**不进下游**（fail the pipeline），宁可不供数、不供坏数。
- 告警分级：结构破坏/行数骤降 = 页面级；单条规则失败 = 工单级。
- 质量报告例行化：通过率、失败明细周报——质量是持续运营，不是一次性清洗。

## 收尾清单

六维检查表覆盖关键表 / 金字塔三层都有 / 关键列优先不全测 / 数据合同显式化 / 新鲜度 SLA 监控 / 失败阻断不供坏数。

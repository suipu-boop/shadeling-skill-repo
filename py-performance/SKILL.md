# Python 性能优化

铁律只有一条：**先测量，再优化**。凭感觉优化 = 优化不存在的问题。

## 第一步：剖析定位

- **CPU**：`cProfile` 找最耗时函数；`line_profiler` 下钻到行级；生产环境用 `py-spy` 无侵入采样。
- **内存**：`memory_profiler` 看分配峰值与泄漏点。
- **计时**：粗测用 `time.perf_counter()`；公平对比用 `timeit`（多轮取平均）。

测出热路径再动手——热点往往不在你猜的地方。

## 高收益清单（按性价比排序）

**数据结构选对**（常常一个改动砍掉一整类开销）：
- 查找用 `dict`，成员判断用 `set`——别在 `list` 上写 `in` 循环。
- 大数据流用**生成器**逐个产出，别先造完整列表占内存。

**缓存重复计算**：
- 纯函数加 `functools.lru_cache`，相同的入参直接命中。
- 注意只缓存真·纯函数（有副作用或依赖外部状态的会出 bug）。

**减少拷贝与拼接**：
- 字符串拼接用 `"".join(parts)`，别在循环里 `+=`（每次都新建）。
- 遍历时尽量原地操作，避免不必要的切片与复制。

**批量 IO**：
- 数据库操作合并成批量（ executemany、批量插入），N 次往返变 1 次。
- 连接池常驻，别每请求新建连接。

**内置优先**：`sum`/`min`/`sorted` 等内置函数是 C 实现，比手写循环快且不易错；数值密集用 NumPy 向量化。

**并行要选对轴**：
- CPU 密集 → 多进程（绕开 GIL）。
- IO 密集 → 异步或线程池（等待时可让路）。

## 常见坑

- 没剖析就优化（最常见，也最浪费）。
- 过度优化冷路径——99% 时间不跑的代码不值得动。
- 算法复杂度没看住：O(n²) 套在数据量增长的业务上，微优化救不了。
- 忽略内存：只盯时间不盯峰值，服务被 OOM 杀死。
- 过早优化牺牲可读性——**先清晰，后提速**；优化过的热路径补注释与基准测试。

## 验证闭环

优化前后各测一轮基准（同输入、同环境、timeit 多轮），提速幅度写进提交说明；没有数字的「优化」不许合并。

# 监控看板

监控看板回答两个问题：**服务健康吗（RED）、资源吃得消吗（USE）**——方法论先行，图表是方法论的可视化。

## 两大方法

**RED（管在线服务）**——每个服务四块看板起步：

| 字母 | 指标 | 报警直觉 |
|---|---|---|
| Rate | 每秒请求数 | 骤降 = 上游故障或自己挂了 |
| Errors | 错误率 | >1% 页面级 |
| Duration | 延迟 **P50/P95/P99**（只看均值会埋掉尾部） | P99 超阈值告警 |

**USE（管资源）**——每个资源（CPU/内存/磁盘/连接池）三问：**利用率**（忙的时间占比）、**饱和度**（排队/等待——比利用率早发现问题）、**错误**（计数）。资源监控的重点是饱和度：CPU 80% 还能跑，队列堆积是真要出事。

## 信息层级（一屏之内）

```
大数字区：关键指标现状（请求率/错误率/P99/核心业务量）
   ↓
趋势区：时间序列（默认 6 小时窗口，可切）
   ↓
明细区：表格/热力图（按实例/路由分解）
```

**面板清单速抄**：API 服务 = RED 三块 + 活跃会话 + 缓存命中率 + 队列长度；数据库 = QPS + 连接池使用率 + 查询延迟分位 + 复制延迟 + 慢查询；基础设施 = 节点 CPU/内存/磁盘 IO/网络。

## 指标与采集纪律

- **命名三段式** `前缀_名称_单位`（`http_request_duration_seconds`）——单位进名字，歧义死于摇篮。
- 采集间隔 15-60s；昂贵查询（聚合/分桶）用**录制规则**预计算，别每张图现算。
- 指标基数要克制：label 维度爆炸（user_id 做 label）= 时序库爆炸——高频维度用采样或聚合。
- **监控自己**：采集器自身的健康也进监控——监控静默挂掉等于裸奔。

## 看板即代码

- 看板配置进版本库随代码部署（provisioning/配置文件）——手点出来的看板换环境就丢、改坏无法回滚。
- 复用起步：社区成熟模板打底再按自家指标裁剪——从白板画看板是重复发明轮子。
- 一致性：面板命名、单位、颜色阈值全站统一——红绿语义漂移的看板没法快速读。

## 收尾清单

服务有 RED / 资源有 USE（盯着饱和度）/ 分位数代替均值 / 命名带单位 / 录制规则预计算 / 基数受控 / 看板进版本库 / 监控自身被监控。

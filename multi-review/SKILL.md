# 多维评审

一个评审者查不完所有维度（安全/性能/架构/测试/无障碍）。多维评审 = **每个维度一个专职评审者并行扫，结果去重汇总**。与评审功夫（单人怎么评）互补，这里管「多人怎么合」。

## 维度分配表

| 维度 | 扫什么 | 何时必上 |
|---|---|---|
| 安全 | 漏洞、鉴权、输入校验 | 碰用户输入或认证就必上 |
| 性能 | 查询效率、内存、缓存 | 动了数据访问或热路径 |
| 架构 | 耦合、分层、模式 | 结构变更或新模块 |
| 测试 | 覆盖、边界、质量 | 新功能 |
| 无障碍 | 可达性、对比度、读屏 | UI 变更 |

## 场景化组合（照抄即可）

| 变更类型 | 维度组合 |
|---|---|
| API 端点 | 安全 + 性能 + 架构 |
| 前端组件 | 架构 + 测试 + 无障碍 |
| 数据库迁移 | 性能 + 架构 |
| 认证变更 | 安全 + 测试 |
| 完整特性 | 安全 + 性能 + 架构 + 测试 |

## 团队规模

| 复杂度 | 人数 |
|---|---|
| 简单（单文件、单关注点） | 1-2 |
| 中等（多文件、2-3 关注点） | 2-3 |
| 复杂（跨切面、大特性） | 3-4 |

拇指法则：**从能覆盖全部所需维度的最小团队起步**——每加一人都是协调成本。

## 发现项去重（多人评审的脏活）

多评审者必然撞车，合并规则：

1. 同位置同问题 → **合并**一条，署名全部发现者
2. 同位置不同问题 → 各自保留
3. 同问题不同位置 → 保留多条，交叉引用（一处修复可能处处复制）
4. 严重度打架 → **就高不就低**
5. 修法打架 → 两个方案都列出、附各自理由，升级仲裁

## 汇总产线

去重后的发现项统一分级（阻断/重要/建议，同评审功夫的标签法）→ 同一文件的意见合并成一条评审意见（别对作者开 15 个炮口）→ 修复后按维度复核。评审者之间不互改结论——仲裁走人，不走吵架。

## 收尾清单

维度按变更类型配齐 / 组合照表抄 / 去重五规则执行 / 严重度就高 / 汇总后统一输出 / 有仲裁路径。

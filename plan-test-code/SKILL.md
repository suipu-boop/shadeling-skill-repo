实施计划

目标

在动手写代码之前，把已确认的需求或设计拆成一份可直接照着做的实施计划。假设执行者熟悉开发、但对本项目几乎零上下文：为每一步写清要改哪些文件、写什么代码、怎么验证。

开始写作前先说明："我正在用「实施计划」技能来生成计划。"

范围检查

如果需求覆盖多个互不依赖的子系统，先建议拆成多份计划，每份对应一个子系统；每份计划都应能独立产出可运行、可验证的成果。

文件结构

先定任务之前，先列出本次会新建/修改哪些文件、各自负责什么。

- 每个文件只承担一个清晰职责；能用小文件就不用大文件。
- 一起改动的文件放在一起，按职责切分而不是按技术分层。
- 在已有代码库里沿用既有组织方式；若待改文件已臃肿，可在计划中包含拆分。

任务粒度

任务是能自带一轮测试、值得单独验收的最小单元。

- 每个任务结束时都应有可独立验证的成果；把配置、脚手架、文档等步骤并入需要它们的那一步。
- 每一步只做一件事（约 2–5 分钟）：「写失败的测试」→「确认它失败」→「写最小实现」→「确认测试通过」→「提交」。

计划文档结构

每份计划以固定头部开始：目标（一句话）、方案（2–3 句）、关键依赖、约束（版本下限、命名规则等逐条列出）。

每个任务包含：

- 改动文件：新建 / 修改（含行号区间）/ 测试文件的确切路径；
- 接口：本任务用到的上游产出（确切签名），以及本任务对外提供的函数名与参数、返回类型；
- 步骤：带勾选框的逐步清单，每一步都给出实际内容。

禁止占位符

不得出现「待定」「稍后补充」「加上适当的错误处理」这类空话；不得写「与任务 N 类似」而不重复代码；涉及代码的步骤必须给出可直接使用的代码块；不得引用任何未定义的类型、函数或方法。

自检

计划写完后对照需求自查三件事：

1. 覆盖度：需求每一节是否都能对应到某个任务？列出缺口并补上。
2. 占位符扫描：按上节清单逐条排查，就地修掉。
3. 一致性：后面任务用到的类型、签名、属性名是否与前面定义的一致。

发现问题直接就地修正，然后交付计划，并说明后续可由执行者逐任务推进、在任务之间设置检查点。

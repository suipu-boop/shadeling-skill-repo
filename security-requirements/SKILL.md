# 安全需求

「要安全」不是需求——**不可测试的安全要求等于没提**。三步把安全意图变成可验收的任务。

## 三级分解

```
业务目标          →  安全需求            →  技术控制
「保护客户数据」      「PII 存储加密」         「AES-256 + 密钥轮换」
```

每级都要能往下落一层；落不下去的需求（「系统应当安全」）退回去重写。

## 三类安全需求

| 类型 | 关注点 | 例 |
|---|---|---|
| 功能性 | 系统必须做的事 | 「系统必须对用户做认证」 |
| 非功能性 | 必须做到什么程度 | 「认证完成 < 2 秒」 |
| 约束 | 强加的限制 | 「只用审批过的密码学库」 |

## 可测试化改写

模板：**[对象] 在 [条件] 下 必须 [可验证的行为]**。

- 坏：「密码要安全存储」
- 好：「用户密码以 bcrypt（cost≥12）加盐哈希存储，数据库字段中不得出现明文或可逆密文（验收：检查存储层字段格式）」

每条需求四属性齐才合格：**可追溯**（链到具体威胁/合规条款）、**可测试**（有明确验收方法）、**有优先级**、**有风险等级**（不满足时的影响）。

## 追溯链

威胁模型（见威胁建模技能）的每条高优先级威胁，至少映射一条安全需求；每条需求映射到具体控制与测试用例。合规场景同理：合规条款 → 需求 → 控制 → 测试，四层链路任何一环断掉 = 审计风险。

反向价值：安全测试用例失败时，沿链上溯能定位是哪条需求、哪个威胁的防线失效——安全工作从「 checklist 」变成「风险驱动的闭环」。

## 收尾清单

需求可测试化改写 / 四属性齐全 / 威胁全映射 / 控制可落地 / 链路四层无断环 / 随威胁模型同步更新。

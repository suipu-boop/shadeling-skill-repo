# 认证授权模式

先分清两件事：**认证（AuthN）回答「你是谁」**——验身份、发凭证、管登录登出；**授权（AuthZ）回答「你能干什么」**——权限检查、角色控制、资源归属。两套机制，别混着做。

## 认证三条路线

| 方案 | 原理 | 适用 |
|---|---|---|
| 会话（session） | 服务端存状态，cookie 放会话 ID | 传统 Web 应用，简单可控 |
| JWT（令牌） | 无状态自包含，声明存令牌里 | API 服务、水平扩展 |
| OAuth2 / OIDC | 委托认证给身份提供商 | 社交登录、企业 SSO |

**JWT 要点**：短期有效（15-30 分钟）+ 刷新令牌换新；**放 httpOnly cookie，不放 localStorage**（XSS 直接偷走）；签名密钥定期轮换。
**会话要点**：cookie 四件套 httpOnly + secure + sameSite + 过期；服务端可主动踢人（JWT 做不到，这是它换来的扩展性）。

## 授权模型：RBAC

角色为桥：用户 → 角色 → 权限。

- 先查「有没有权限」再进业务逻辑，**服务端执行**（前端隐藏按钮只是体验，不是安全）。
- 资源归属校验单独做：登录不等于能看——「能看订单列表」≠「能看任何人的订单」。
- 更细的场景用权限点模型（permission-based）替代角色爆炸。

## 安全红线清单

- 密码永不落明文：bcrypt/argon2 加盐哈希
- 全站 HTTPS；传输不加密 = 全裸
- 认证端点限速：防暴力破解（错误次数锁定/退避）
- 登录成功/失败都记安全日志（配合可观测性技能）
- 密码重置走带过期的安全令牌，别设计成猜谜
- 支持 MFA 就上 MFA
- 客户端传来的身份信息一律不信，服务端重新校验

## 常见坑

- JWT 无过期时间 / 过期设太长
- 只在前端做权限判断
- 密码策略形同虚设（「123456」能过）
- 重置流程泄露存在性信息（「该邮箱未注册」帮攻击者筛选账号）
- 升级认证体系没有过渡期（新旧并存时旧通道就是漏洞）

## 收尾清单

认证授权分离 / 令牌短期且能刷新 / cookie 安全四件套 / 服务端强校验 / 端点限速 / 安全事件有日志 / 密码哈希正确。

# 提示工程模式

把「调提示」从玄学变成工程：每个模式解决一类不稳定。

## 少样本（few-shot）

模型模仿力强于理解力。给 2-5 个**边界覆盖**的示例——不只给典型例，专门给「容易错的」：含糊输入、特殊情况、期望拒绝的输入。示例格式必须与真实输入**完全一致**（同一模板渲染），否则模型学歪。

## 思维链（CoT）

推理类任务，让模型**先写推理过程再给答案**：「先逐步分析，最后给出结论」。推理步骤本身就是可检查的中间产物——错了能定位哪步跑偏。注意：简单任务别硬上 CoT，纯增延迟。

## 结构化输出

把「输出 JSON」的祈祷换成 schema 约束：

```python
class SQLQuery(BaseModel):
    query: str = Field(description="The SQL query")
    explanation: str = Field(description="Brief explanation")
    tables_used: list[str] = Field(description="Tables referenced")

structured_llm = llm.with_structured_output(SQLQuery)
```

- schema 即文档：字段描述写清约束（格式、单位、可选值）。
- 结构化输出 + 校验器（pydantic）+ 校验失败重试 = 生产可用的管道。
- 模型偶尔不听话是常态，**校验兜底**才是设计的一部分。

## 系统提示设计

- 角色一句话讲清（「你是 SQL 专家」），别写小作文。
- 硬约束显式列出（「总是用参数化查询」「无法回答就直说不知道」）。
- 输出格式要求放系统提示，用户消息只装数据——两层别混。
- 长系统提示里，**开头与结尾**的内容权重最高，关键约束放这两处。

## 模板化

提示是代码不是散文：进版本库、走评审、有回归测试集。改提示 = 改代码，跑测试集对比再合入。

## 评估闭环（与 llm-evaluation 配套）

- 建**黄金测试集**：典型 + 边界 + 历史翻车案例。
- 每次改提示跑一遍，通过率有数字。
- 线上采样抽查，坏例回流测试集。

## 常见坑

- 示例与真实输入格式不一致（最高频翻车）
- 让模型「不要编造」却没给逃生门（应说「不确定就回答 UNKNOWN」）
- 提示越写越长全堆用户消息——分层：系统约束/少样本/当前输入
- 一次改多处——一次改一处，跑了测试集再说

## 收尾清单

少样本含边界例 / 推理类有 CoT / 输出走 schema 校验 / 系统提示分层清晰 / 提示进版本库 / 有黄金测试集。

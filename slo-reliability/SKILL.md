# 可靠性目标（SLO）

可靠性的谈判桌：**多可靠才算够？** SLO 把这个问题变成可管理的数字，而不是永远的「越稳越好」。

## 三层结构

```
SLA  ← 对客户的合同承诺（违反赔钱）
SLO  ← 内部可靠性目标（违反触发行动）
SLI  ← 实际测量指标（客观事实）
```

SLI 测量、SLO 定标、SLA 兜合同——方向自下而上支撑，数字自上而下留余量（SLO 比 SLA 严一点，留操作空间）。

## 常用 SLI

- **可用性**：成功请求数 / 总请求数（5xx 算失败；4xx 算不算按业务定——用户输错密码不该算服务不可用）
- **延迟**：低于阈值的请求占比（「P99 < 500ms」不如「99% 请求 < 500ms」好测——前者是分位数 SLO，后者是比例 SLO）
- **新鲜度**：数据更新延迟（读模型落后多少算过期）
- **正确性**：写入成功留存率

选型原则：SLI 必须**从用户视角测量**——服务器 CPU 再闲，用户打不开就是不可用。

## 定目标：够用即可

| SLO | 月停机预算 | 适用 |
|---|---|---|
| 99% | 7.2 小时 | 内部工具 |
| 99.9% | 43.2 分钟 | 一般线上服务 |
| 99.95% | 21.6 分钟 | 核心业务 |
| 99.99% | 4.3 分钟 | 金融/生命线（成本陡增，慎选） |

每个 9 都是十倍成本。**问「用户会在乎吗」**：内部工具定 99.99% 是烧钱行为艺术；核心支付定 99% 是拿业务冒险。

## 错误预算：SLO 的精髓

错误预算 = 1 − SLO。99.9% 的月预算 = 43.2 分钟的「允许失败额度」。

- **预算充足**：放开手脚——发版、实验、快速迭代都放行。
- **预算耗尽**：冻结非紧急发版，全员转可靠性改进——这是**制度化的平衡**，创新与稳定不再靠吵架解决。
- 预算按滚动窗口（28 天常见）计算，烧穿告警分级（50% 预警、90% 冻结）。

## 落地纪律

- SLO 少而精：每服务 2-3 个核心 SLI 足够，仪表盘堆满没人看。
- 没有错误预算的 SLO 只是装饰——预算机制（烧穿冻结发版）才是牙齿。
- 目标定期校准：连续一年轻松达标说明定低了，浪费迭代速度；反复打穿说明定高了或服务真有问题。

## 收尾清单

SLI 从用户视角测 / SLO 够用不镀金 / 错误预算机制有牙齿（冻结规则）/ 预算告警分级 / 目标年度校准。

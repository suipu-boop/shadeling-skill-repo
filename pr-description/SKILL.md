# PR 描述

PR 描述只回答三个问题：**改了什么、凭什么说改对了、合并有什么风险**。三段之外的客套全是噪音。

## 三段模板

### 1. Summary——一张图胜千言

放一个示意图、diff 草图或目录树，让评审 10 秒看懂改动形状。文字只补图说不清的动机。

### 2. Evidence——改对了的证据

- **改前**：截图/输出/失败的测试运行
- **改后**：截图/输出/通过的测试运行

证据必须是真实跑出来的东西，不是「已测试」三个字。

### 3. Merge Danger——合并风险

- **Door（单双向）**：单向门（合了难回退，如 schema 变更、删接口）还是双向门（随时可 revert）？单向门必须标注。
- **Blast Radius（波及面）**：一个词概括可能炸到哪里（如「所有调用方」「仅此模块」），可附两句具体后果。

## 写作纪律

- **零开场白**：不写「这个 PR 主要……」，直接进三段。
- **用领域语言**：项目术语表里已有的词照用，不发明新叫法。
- **评审视角**：写完自问——评审者只看这段能不能决定「批还是不批」？不能，就补证据。

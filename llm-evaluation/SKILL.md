# LLM 评估

没有测量的改进是错觉。LLM 应用三轨评估，缺一不可。

## 前提：黄金测试集

先建测试集，再谈评估：

- **典型例**（60%）：日常主流输入
- **边界例**（25%）：超长输入、混合语言、对抗构造、模糊指令
- **历史翻车例**（15%）：线上坏例回流——这块最值钱

每例带期望结果或评分要点。测试集进版本库，与代码同轨演化。

## 三轨评估

**1. 自动指标（便宜、每轮跑）**
按任务类型选：
- 抽取/分类类：精确率、召回率、F1
- 生成类：ROUGE/BLEU 只当粗筛（与人工相关性弱）；语义相似度（embedding 余弦）看内容漂移
- 工程类指标同样要测：延迟 P95、成本/次、结构化输出解析成功率

**2. 人工评估（贵、抽样跑）**
- 每版本随机抽 30-100 例，双盲打分（评分者不知道是哪个版本）
- 评分维度拆开：事实正确性、相关性、格式合规、语气——一个综合分掩盖问题
- 记录评审者间一致性；分歧大的例子上测试集

**3. LLM-as-judge（折中、可放量）**
让强模型按 rubric 打分，先**校准**：与人工评分对齐（相关性 >0.8）才能上岗。
- rubric 明确到可操作（「引用了上下文中不存在的信息 = 0 分」）
- 防位置偏差：交换候选顺序各评一次取均值
- 防自我偏好：裁判模型与被评模型别同款

## 集成到工作流

- 改提示/换模型/调参数 → 必跑自动指标全量 + LLM-judge 抽样
- 版本间对比出报告（指标 delta + 坏例清单），有数字才准合入
- 线上持续采样 → 坏例回流测试集 → 测试集驱动下一轮改进

## 常见坑

- 只看一个综合分——维度拆开才见真相
- 测试集一成不变——模型会「过拟合」在旧集上，定期换血
- judge 不校准直接上岗——打分离人工差十万八千里
- 忽略工程指标——质量上去了延迟爆了也是失败

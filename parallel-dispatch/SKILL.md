## 概述

把任务委派给带隔离上下文的专职代理。**精心构造**它们的指令与上下文，确保它们聚焦并成功。它们**绝不继承**你会话的上下文或历史——你构造的正是它们需要的东西。这也保住了你自己的上下文，留给协调工作。

多个不相干的故障（不同测试文件、不同子系统、不同 bug）按顺序挨个查是浪费时间。每个调查都独立，可以并行。

**核心原则：** 每个独立问题域派一个代理，让它们并发跑。

## 什么时候用

- 3 个以上测试文件挂了，根因各不相同
- 多个子系统各自独立地坏了
- 每个问题不需要别人的上下文就能理解
- 调查之间无共享状态

**别用：**
- 故障相关（修一个可能顺带修好其他）
- 需要理解全系统状态
- 代理之间会互相干扰

## 模式

### 1. 识别独立域

按坏的东西分组：文件 A 的测试管工具审批流，文件 B 的测试管批量完成行为，文件 C 的测试管中断功能。三个域独立——修审批流不影响中断测试。

### 2. 造聚焦的代理任务

每个代理拿到：**具体范围**（一个测试文件/子系统）、**清晰目标**（让这些测试过）、**约束**（别动别的代码）、**期望输出**（找到什么、修了什么的总结）。

### 3. 并行派发

所有派发放在**同一个回应里**发出——它们就并行跑。多次派发分多个回应 = 串行。

### 4. 收回与整合

代理回来后：读每份总结；核对修复互不冲突；跑全量测试；整合全部改动。

## 代理提示词结构

好的代理提示词：**聚焦**（一个清晰问题域）、**自包含**（理解问题所需的全部上下文）、**输出明确**（说清代理该返回什么）。

```markdown
修 src/agents/agent-tool-abort.test.ts 里挂的 3 个测试：

1. "should abort tool with partial output capture" - 期望消息含 'interrupted at'
2. "should handle mixed completed and aborted tools" - 快工具被中断后状态不对
3. "should properly track pendingToolCount" - 期望 3 个结果，实际 0

这些是时序/竞态问题。你的任务：
1. 读测试文件，弄清每个测试验证什么
2. 找根因——是时序问题还是真 bug？
3. 修复方式：
   - 把拍脑袋的超时换成基于事件的等待
   - 找到中断实现里的真 bug 就修掉
   - 测试期望本身过时了就调整期望

不许只调大超时——找到真问题。

返回：找到什么、修了什么的总结。
```

## 常见错误

- ❌ 太宽泛：「把所有测试修好」——代理会迷路 → ✅ 具体：「修 agent-tool-abort.test.ts」
- ❌ 没上下文：「修那个竞态」——代理不知道在哪 → ✅ 给上下文：贴错误信息和测试名
- ❌ 没约束：代理可能重构一切 → ✅ 约束：「别动生产代码」「只修测试」
- ❌ 输出含糊：「修好它」→ ✅ 明确：「返回根因和改动总结」

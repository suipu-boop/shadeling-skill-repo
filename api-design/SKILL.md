# API 设计原则

目标：让调用方**猜都猜得对**。可预期性是接口设计的最高美德。

## 资源导向

- URL 是名词（`/users`、`/orders`），动作交给 HTTP 方法：GET 查（幂等安全）、POST 建、PUT 全量替换（幂等）、PATCH 局部改、DELETE 删（幂等）。
- 层级表达归属：`/users/{id}/orders`；过深的层级（>2 层）改用查询参数。
- 集合用复数、命名全小写中划线、风格全 API 一致——**一致性 > 个人偏好**。

## 状态码用对

- 2xx 成功（201 建成附 Location、204 无返回体）
- 4xx 客户端的错：400 参数错、401 未认证、403 无权限、404 不存在、409 冲突、429 限速
- 5xx 服务端的错：别把业务错误塞 500
- 错误响应结构统一：错误码 + 人话消息 + 可执行的提示，全 API 一个格式

## 版本化：第一天就想好

- URL 版本最直白：`/api/v1/users`（推荐，路由清晰）
- Header 版本更「纯」但调试不直观：`Accept: application/vnd.api+json; version=1`
- 破坏性变更 = 新版本；旧版本给迁移期并公示下线时间；字段只加不删，删前先标废弃。

## 分页与限速

- 集合接口**必须**分页：`page/page_size` 简单够用；数据大且要求稳定用游标（`cursor`）——深翻页不衰减。
- 响应带总数与下一页指针，让客户端不用猜。
- 限速保护自己：返回 429 时附 `Retry-After` 头（对端是程序，它只看头）。

## GraphQL 补充（若用）

- schema 先行：类型即领域模型，写 resolver 前先定 schema
- 防 N+1：DataLoader 批量合并取数
- 查询复杂度限制与深度限制（防恶意深挖）
- 分页走 Relay 游标规范

## 常见坑

- 动词 URL（`/getUser`）——方法语义白瞎了
- 200 里包错误体——监控系统全瞎
- 无版本化，第一次破坏性变更时后悔
- 无分页，数据涨了接口崩
- 文档事后补——用 OpenAPI 注解随代码生成，文档和代码永不脱节

## 收尾清单

资源名词化 / 方法语义正确 / 状态码不乱用 / 错误结构统一 / 已版本化 / 集合已分页 / 有限速 / 文档自动生成。

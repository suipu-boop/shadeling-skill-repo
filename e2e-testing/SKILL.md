# 端到端测试

E2E 慢、脆、贵，所以纪律比数量重要：**少而准**，只测用单元测试和集成测试覆盖不了的关键路径。

## 测试金字塔（数量配比）

```text
        /\
       /E2E\        ← 极少：登录、下单、注册等关键旅程
      /─────\
     / 集成  \      ← 中等：组件/服务间交互、API 契约
    /─────────\
   /  单元测试  \    ← 海量：快、隔离、毫秒级
  /─────────────\
```

## 该测什么、不该测什么

**该测**：关键用户旅程（登录、支付、注册）、复杂多步交互（拖拽、向导表单）、跨浏览器兼容、真实 API 集成、认证流。

**不该测**：单元级逻辑（用单测）、API 契约细节（用集成测试）、极端边界（E2E 太慢）、内部实现（重构就碎）。

## 八条最佳实践

1. **data-testid 做选择器**——永不依赖 CSS 类名或 DOM 层级。
2. **测用户行为不测实现**：点按钮、填表单、看结果——不是断言内部状态。
3. **测试相互独立**：每条自备数据、自清数据，不依赖执行顺序。
4. **页面对象模式**：页面结构封装在一处，改版只改一处。
5. **断言用户可见的结果**，不是中间变量。
6. **能 mock 外部就 mock**（第三方支付、短信），自己家的后端走真实。
7. **并行执行**，套件控制在分钟级。
8. 每条测试**自说明**：名字讲清楚「谁在什么场景下做什么、期望什么」。

## flaky 根治（比新增测试更优先）

- **等待条件而不是等待时间**：等元素出现/网络返回，绝不 `sleep(3)`。
- flaky 三大根因：竞态（用条件等待解决）、测试间污染（自备自清数据）、环境抖动（容器化、隔离外部依赖）。
- **flaky 立即隔离**：进隔离区，修好或删掉，绝不让它反复污染主干置信度。
- 一条测试连续失败但代码没变 → 先怀疑测试本身。

## 常见反模式

- 用 E2E 补单元测试的课（慢十倍还脆）。
- 选择器写 `div > form > div:nth-child(2)`（改版即碎）。
- 一条测试里塞多个旅程（失败定位地狱）。
- CI 里跑全套 E2E 每个 PR（只跑冒烟子集，全套夜间跑）。

# 分层架构

一个铁律三种呈现：**依赖只能向内指**——业务核心不认识框架、数据库和外部世界。

## 三种分层法

**干净架构（Clean Architecture）**：四环，由内向外 = 实体（纯业务模型，零框架 import）→ 用例（编排实体的应用规则）→ 接口适配器（控制器/网关，翻译格式）→ 框架与驱动（UI/数据库/外部服务）。每层边界都走抽象接口，内层对外层零所知。

**六边形（端口与适配器）**：领域核心 + 端口（核心对外的抽象接口，分驱动与被驱动两侧）+ 适配器（端口的具体实现，如 PostgreSQL 适配器）。收益：换实现不动核心（PostgreSQL 换 DynamoDB 只换适配器）；测试用内存适配器，不需要 Docker；技术选型推迟到边缘。

**DDD（领域驱动设计）**：
- 战略：限界上下文（每个子域一套内聚模型，别全系统共享一个大模型）、上下文映射（防腐层隔离外部模型）、统一语言（代码里的词 = 领域专家嘴里的词）。
- 战术：实体（有稳定身份）、值对象（不可变、按属性判等：Email/Money/Address）、聚合（一致性边界，外部只碰聚合根）、仓储（聚合的存取抽象）、领域事件（跨聚合协调用事件不用调用）。

## 五类腐化症状与对治

| 症状 | 病根 | 药方 |
|---|---|---|
| 用例测试要起真数据库 | 业务逻辑漏进基础设施层 | 数据库调用全部藏到仓储接口后，测试注入内存实现；用例构造器收抽象端口不收具体类 |
| 层间循环 import | 用例 import 了具体适配器 | 铁律：用例层只 import 领域层（实体+接口），永不碰适配器/基础设施 |
| 领域实体上出现框架注解 | 实体不纯了 | 实体归实体，ORM 模型放适配器层，仓储里做双向映射 |
| 逻辑全堆在控制器 | 控制器越界 | 控制器只干三件事：解析请求、调用例、组响应 |
| 值对象报错太晚 | 构造时没校验 | 不变量在构造函数里验，非法 Email 活不到被使用的那天 |

## 测试分层

用例测试配内存适配器（假仓储）——不碰真库、毫秒级、可并发；适配器测试才碰真实现（真库跑集成测试）。这样业务规则测试既快又稳，架构分层是否干净，看测试要不要外部依赖就知道了。

## 收尾清单

依赖单向向内 / 边界全是抽象接口 / 实体零框架污染 / 控制器三件事 / 值对象构造即校验 / 用例测试不起外部依赖。

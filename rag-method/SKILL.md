# RAG 落地

四件套：**向量库、嵌入、检索策略、重排**。框架怎么换这四件事不变——先懂原理再选工具。

## 1. 向量库选型

| 诉求 | 选 |
|---|---|
| 托管省心、可扩展 | Pinecone |
| 开源、自带混合检索 | Weaviate / Qdrant |
| 本地轻量开发 | Chroma |
| 已有 PostgreSQL | pgvector（少一个组件） |

选型三问：数据量级、要不要过滤检索（metadata filter）、运维成本谁担。

## 2. 嵌入模型

- 选型看：维度（存算成本）、语言匹配（中文场景选多语或中文特调模型）、榜单成绩只是起点。
- **全库统一一个模型**：嵌入模型一换，全量重嵌——这是 RAG 最大的迁移成本，选型慎重。
- 分块策略比模型选择更影响效果：语义完整优先（按段落/标题切），块大小 300-800 token 起步再调，块间留重叠防截断。

## 3. 检索策略（按性价比递进）

1. **稠密检索**：语义相似，同义改写能命中，但专名/编号弱
2. **稀疏检索**：BM25 关键词匹配，专名精准，语义泛化弱
3. **混合检索**：稠密+稀疏加权融合（RRF 常用）——**默认起点**，两者互补
4. **多查询**：让模型把问题改写成多个变体分别检索再合并
5. **HyDE**：先让模型生成假想答案，用它去检索（假想答案与真文档更相似）

## 4. 重排（rerank）

初检召回靠宽，精排靠准：cross-encoder 对「问题-候选」逐对精细打分，取 Top k 送入生成。性价比最高的一步——初检放宽到 50-100 条，重排后只留 3-5 条，上下文又准又省。

## 系统提示铁律

- 「仅根据以下上下文回答，上下文没有就直说不知道」——给模型逃生门，抑制编造。
- 引用溯源：答案标注来源块编号，用户可核。
- 上下文放「问题前」，格式统一（来源、标题、正文三段式）。

## 评估闭环

- **检索层**单独评：黄金问答集上测命中率（recall@k）——检索不行生成再好也白搭
- **端到端**评：答案正确性 + 忠实度（答案是否被上下文支撑）+ 拒答正确性（该拒的拒了没）
- 三层各自可换：嵌入、检索、重排逐层消融，看每步的真实贡献

## 常见坑

- 分块过大过碎——过大检索不准，过碎语义断裂
- 只做稠密检索——专名查询全军覆没
- 不评检索层直接评端到端——归因失明
- 嵌入模型随手换——全库重嵌成本没算过
- 上下文塞太满——多不等于准，重排后精挑才是正道

## 收尾清单

分块语义完整 / 混合检索起步 / 重排已上 / 系统提示有逃生门 / 答案带溯源 / 检索层单独有评估。

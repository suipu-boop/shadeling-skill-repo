# 混合检索

纯向量检索的软肋：**专有名词、编号、代码**这类精确 token 匹配场景反而不如老式关键词检索。混合检索 = 两条腿走路。

## 架构

```
查询 → ┬→ 向量检索（语义路）→ 候选 ┐
       └→ 关键词检索（精确路）→ 候选 ┴→ 融合 → 重排 → 结果
```

- 向量路管「意思相近」，关键词路管「字面命中」（人名/型号/错误码）。
- 两路各自出候选（各 top 20-50），融合后统一排序。

## 融合方法

| 方法 | 原理 | 何时用 |
|---|---|---|
| **RRF**（倒数排名融合） | 按排名倒数加权，不比原始分 | **默认首选**——免调参、两路分数量纲无关 |
| 线性加权 | 分数归一后加权求和 | 需要精细控制两路偏重时 |
| 级联 | 一路粗筛另一路精排 | 延迟敏感场景 |
| 交叉编码重排 | 神经模型对 query-候选逐对打分 | 质量上限最高，成本最高 |

## 落地要点

- **RRF 起步**：免归一化免调参，效果稳——先跑起来再考虑加权。
- **重排器加一层**：融合出 top 50，交叉编码重排取 top 5 送下游——质量提升最显著的一步（延迟预算内）。
- **两路分数都记日志**：排障时看得见「哪路召回了什么」——只记融合结果没法归因。
- **A/B 定权重**：在自家检索金标集上测（见嵌入选型的金标思路），不同查询类型最优配比不同——「一套参数打天下」是错觉。
- 别过度取回：两路各取太多再融合，延迟炸——候选数在延迟预算内调。

## 收尾清单

双路齐备 / RRF 先行 / 重排层在延迟预算内 / 分数日志双记 / 金标集上 A/B / 空结果与单词查询等边界测过。

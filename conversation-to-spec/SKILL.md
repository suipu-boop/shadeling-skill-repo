# 会话成规格

访谈已把想法磨清，本技能**只综合、不访谈**：把会话里已落定的共识 + 代码库现状，写成一份规格文档。

## 流程

**1. 摸仓库**（若尚未探过）：看清现状；规格全文使用项目词汇表的术语，尊重涉及区域的既有决策记录。

**2. 定测试接缝**——规格里最重要的技术判断：
- 优先复用**既有接缝**，其次新增；接缝尽量选**最高**的；接缝越少越好，理想是一处。
- 向用户确认接缝符合预期，再动笔。

**3. 按模板成文**：

```
## 问题陈述
用户视角的痛点（不是技术描述）。

## 解决方案
用户视角的解法。

## 用户故事
长清单，编号：
1. 作为〈角色〉，我想〈能力〉，以便〈收益〉
覆盖功能的所有方面，宁多勿漏。

## 实现决策
已定的取舍：动哪些模块、接口怎么改、架构决定、数据结构变更、接口契约、
特定交互。**不写具体文件路径与代码片段**（很快过时）；例外：原型里产出的
决策性片段（状态机、schema、类型形状）可内联并注明出处，裁到只剩决策要点。

## 测试决策
什么算好测试（只测外部行为、不测实现细节）、测哪些模块、走哪些接缝。
```

**4. 交付**：发布到项目的问题追踪处并标「代理可执行」标签；无追踪器则存为文档并报告路径。

## 红线

- 全程不再开新访谈；发现真正没定的决策 → 记入「待定」小节，不自行拍板。
- 不写文件级路径（会烂）；用模块名与接口名。
- 用户故事是验收的种子，写不全 = 后面全靠猜。

# 前端状态管理

状态混乱的根因几乎都是一类：**没分类就上全局 store**。先分类、再选工具——「状态放哪」就变成机械题。

## 五类状态（各归各家）

| 类 | 是什么 | 放哪 |
|---|---|---|
| 局部状态 | 单组件 UI 状态（开关、输入） | 组件内 useState/useReducer |
| 全局状态 | 跨组件共享的客户端状态（主题、登录态） | 轻量 store（Zustand/Jotai 类） |
| **服务器状态** | 后端数据的客户端缓存 | 数据缓存库（React Query/SWR 类）——**不是全局 store** |
| URL 状态 | 路由参数、筛选条件 | 地址栏（可分享、可后退、可书签） |
| 表单状态 | 输入值与校验 | 表单库 |

**最大误区**：把服务器返回的数据塞进全局 store 手动管理——缓存失效、重取、竞态全是自己造的。服务器状态有成熟缓存方案，**别重复发明**。

## 选型准则

- 小应用/简单共享 → 轻量 store；大型复杂交互 → 重量级方案；重服务端交互 → 缓存库为主 + 极小客户端状态；细粒度更新（ atoms）→ 原子化库。
- **每类状态选一个主力方案**，全站统一——混用两套全局方案 = 精神分裂。

## 放置纪律

- **就近原则**：状态放得离使用处越近越好——只有「真的跨组件」才上提。过度全局化是状态腐化的起点。
- **派生数据不存**：能从现有状态算出来的（过滤后列表、合计数）就现算或用 memo——存副本必漂移。
- **数据归一**：store 里存扁平结构（按 id 索引），不存深嵌套副本——嵌套对象更新是 bug 温床。
- 选择器订阅：组件只订自己需要的那片状态——整 store 订阅 = 一动全刷。
- 不可变更新：永远造新对象替换，别原地改——引用比较才可靠。

## 收尾清单

五类状态各归各家 / 服务器状态不进 store / 状态就近 / 派生数据现算 / store 扁平归一 / 选择器订阅 / 每类一个主力方案。

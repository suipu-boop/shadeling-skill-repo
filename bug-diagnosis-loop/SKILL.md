难 bug 的纪律。跳过阶段必须有明确理由。

## 保密

本技能会让你展示命令、输出和抓取物。**先脱敏**：密钥一律写 `<REDACTED>`，凭据留在环境变量里而不是展示内容里。抓取物带认证头的，只引用有信号的那几行。脱敏后不足以诊断，直说，向用户要。

## 阶段一：建反馈环（本技能的核心）

**这就是本技能。** 其余全是机械操作。有了这个 bug 的**紧**红/绿信号（对本 bug 会变红的那种），你一定能找到原因——二分、假设检验、插桩都只是在消费这个信号。没有它，盯着代码看到天亮也没用。

在这里花不成比例的精力。**要凶，要有创造力，不许放弃。**

### 构造手段（按大致优先序）

1. 在能够到 bug 的缝上写**失败测试**：单元、集成、端到端皆可。
2. 对运行中的开发服务器发 **curl/HTTP 脚本**。
3. 带固定输入的 **CLI 调用**，stdout 与已知良好快照做 diff。
4. **无头浏览器脚本**驱动 UI，断言 DOM/console/网络。
5. **重放抓取的轨迹**：把真实网络请求/负载/事件日志存盘，隔离重放到出 bug 的代码路径。
6. **一次性测试架**：拉起系统的最小子集（单服务 + mock 依赖），一个函数调用触发 bug 路径。
7. **属性/模糊环**：bug 是「有时输出错」？跑 1000 个随机输入找失败模式。
8. **二分架**：bug 出现在两个已知状态之间？自动化「在状态 X 启动 → 检查 → 重复」，交给 `git bisect run`。
9. **差分环**：同一输入过旧版 vs 新版（或两种配置），diff 输出。
10. **人工在环脚本**。最后手段：必须有人点击时，用结构化脚本驱动人，抓取的输出再喂回你。

建对了环，bug 就修好 90%。

### 拧紧反馈环

把环当产品打磨。有了环就**拧紧**：

- 能更快吗？（缓存准备、跳过无关初始化、缩小测试范围。）
- 信号更利吗？（断言具体症状，不是「没崩」。）
- 更确定吗？（钉死时间、固定随机种子、隔离文件系统、冻结网络。）

30 秒的抖动环几乎等于没环；2 秒的确定环才是调试超能力。

### 非确定性 bug

目标不是干净复现，是**提高复现率**。触发 100 次、并行、加压、缩窄时间窗、注入 sleep。50% 抖动可调试；1% 不可调试——不断提高复现率直到可调试。

### 真的建不出环时

停下，明说。列出试过的手段。向用户要：(a) 能复现的环境访问权，(b) 脱敏的抓取物（HAR、日志转储、core dump、带时间戳的录屏），(c) 临时加生产插桩的许可。**没有环不许进入假设。**

### 阶段一的完成判据：一个能变红的紧环

当环**紧**且**能变红**——你能报出**一条命令**（脚本路径/测试调用/curl），你已经**跑过至少一次**（展示调用与脱敏输出），并且：

- [ ] **能变红**：驱动真实 bug 路径，断言**用户的确切症状**——修好前能红、修好后能绿。不是「能跑不报错」，必须能**抓到这个特定的 bug**。
- [ ] **确定性**：每次跑结论一致（抖动 bug：钉出高复现率，如上）。
- [ ] **快**：秒级，不是分钟级。
- [ ] **可无人值守**：你能自己跑；人工只通过结构化脚本介入。

如果你发现自己在环建成前就开始读代码建理论——**停：跳过复现直奔假设正是本技能要阻止的失败。** 没有能变红的命令，就没有阶段二。

## 阶段二：复现 + 缩小

跑环。看它变红。

确认：

- [ ] 环产生的是**用户描述的**失败模式，不是恰好发生在旁边的另一种失败。错的 bug = 错的修复。
- [ ] 多次运行可复现（非确定性 bug：复现率高到可调试）。
- [ ] 抓到了确切症状（报错信息、错误输出、慢的量化数据），后续阶段好验证修复真的治了它。

### 缩小

红了之后，把复现缩到**仍然变红的最小场景**。输入、调用方、配置、数据、步骤**一次删一个**，每删一个重跑环，只留对失败承重的部分。

为什么值得：最小复现缩小阶段三的假设空间（剩下的活动部件更少），并成为阶段五干净的回归测试。

完成判据：**剩下的每个元素都承重**——删掉任何一个，环就变绿。

**没复现并缩小之前，不许前进。**

## 阶段三：假设

先列 **3-5 个排序的假设**，再动手验证任何一个。单假设生成会锚死在第一个听起来合理的想法上。

每个假设必须**可证伪**：说出它预言什么。

> 格式：「如果 <X> 是原因，那么 <改 Y> 会让 bug 消失 / <改 Z> 会让它更糟。」

说不出预言的假设是气氛组：丢弃或磨尖。

**测试前把排序列表给用户看。** 用户常有领域能力瞬间重排（「我们刚部署了 #3 相关的改动」），或知道你列的假设早被排除过。便宜的检查点，省大时间。用户不在也别堵着：按自己的排序继续。

## 阶段四：插桩

每个探针对应阶段三的一个具体预言。**一次只动一个变量。**

工具偏好：

1. 环境 支持就上**调试器/REPL 检查**。一个断点胜过十条日志。
2. 在能区分假设的边界上打**定点日志**。
3. 永远不要「全打出来再 grep」。

**每条调试日志打唯一前缀**，如 `[DEBUG-a4f2]`。收尾时一个 grep 清干净。不打标的日志会存活；打标的日志会死。

**性能分支**：性能回退通常不该用日志。改用：先建立基线测量（计时架、profiler、查询计划），再二分。先测量，后修复。

## 阶段五：修复 + 回归测试

修复之前写回归测试——但仅当存在**正确的缝**。

正确的缝：测试在调用现场真实发生的 bug 模式。若唯一的缝太浅（bug 需要多调用方，测试只有单调用方；单元测试复现不了触发链），那里的回归测试给出的是虚假信心。

**不存在正确的缝，这本身就是发现。** 记下来：代码库的结构在阻止 bug 被锁定。标记给下一阶段。

有正确缝时：

1. 把最小复现变成缝上的失败测试。
2. 看它失败。
3. 上修复。
4. 看它通过。
5. 用阶段一的环对原始（未缩小的）场景重跑。

## 阶段六：清理

宣布完成前必须：

- [ ] 原始复现场景不再复现（重跑阶段一的环）
- [ ] 回归测试通过（或「无缝可测」已记录在案）
- [ ] 所有 `[DEBUG-...]` 插桩已移除（grep 前缀）
- [ ] 一次性测试架已删（或移到明确标记的调试位置）
- [ ] 被证实的那个假设写进了提交/PR 说明——让下一个调试的人学到

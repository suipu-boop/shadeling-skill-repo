# 微服务模式

拆是为了**独立部署与独立演化**，不是为了时髦。边界拆错的微服务比单体更糟。

## 怎么拆

**按业务能力拆**（首选）：一个服务一个业务职能（订单/支付/库存），各自拥有领域、独立部署。
**按子域拆（DDD）**：核心域自建精做，支撑域可采购，限界上下文 ≈ 服务边界。
**绞杀者模式（迁移利器）**：不推倒重来——新功能做成新服务，代理层把流量逐渐从单体路由过去，旧功能按节奏搬空后退役。单体是**渐进变薄**的。

**反面信号**：拆出来的服务要同步调用其他服务才能完成一个业务动作 = 边界切错了；两个服务总是同生共死地发版 = 本来就是一个服务。

## 通信

- **同步（REST/gRPC）**：简单直观，但把延迟与故障串联起来——调用链越长越脆。
- **异步（事件/消息）**：服务间用事件解耦，故障不传播、吞吐可削峰——**跨服务协作默认选异步**。
- 事件契约是公共 API 的一部分：schema 进版本库、向后兼容、消费者只认契约不认实现。

## 数据

**每服务一库**是铁律：共享数据库 = 把单体最难拆的部分（耦合的数据模型）焊死。跨服务数据可见性走事件投影（对方订阅你的变更事件自建只读副本），不走直连对方的库。

**跨服务事务 = Saga**（见 Saga 编排技能）：分布式锁和两阶段提交都别碰，用补偿。

## 防雪崩三件套

- **断路器**：连续失败即熔断快速失败，给下游喘息；半开试探恢复。
- **重试带退避**：只重试瞬时故障（同韧性模式技能），配重试预算防重试风暴。
- **舱壁**：资源隔离（连接池/线程池按下游分池），一个下游拖死不殃及全体。

## 常见坑

- 分布式单体：服务拆了、部署还是绑着一起发——只得了分布式的复杂度，没拿到独立性
- 共享数据库（最常见也最难回头）
- 同步调用链过长：A→B→C→D，任一抖动全链超时
- 无链路追踪就上微服务——分布式排障没 trace 是瞎子（关联 ID 铁律见可观测性技能）
- 一开始就微服务——先单体长出清晰模块边界，再按绞杀者渐拆

## 收尾清单

边界按业务能力 / 跨服务默认异步 / 每服务一库 / 跨服务事务走补偿 / 断路器+舱壁在位 / 全链 trace 通。

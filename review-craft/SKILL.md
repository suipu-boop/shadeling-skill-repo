# 评审功夫

与双轴审查（dual-axis-review，流程向）互补：那个管「审什么维度」，这个管「怎么把评审做的好」。

## 心态：评审为了什么

- **是**：抓 bug 与边界、保可维护性、传知识、守规范。
- **不是**：炫耀学问、挑格式（那是 linter 的活）、卡进度、按个人口味重写。

好反馈四要素：**具体可执行、教育而非评判、对代码不对人、有褒有贬**。

```text
坏：「这写错了。」
好：「多用户同时访问会出竞态，这里考虑加锁。」

坏：「为什么不用 X 模式？」
好：「考虑过仓储模式吗？会更好测，示例见链接。」

坏：「改名。」
好：「[nit] 建议用 userCount 代替 uc，更清楚。不阻塞。」
```

## 审什么、不审什么

**人工审**：逻辑正确性与边界、安全漏洞、性能影响、测试覆盖与质量、错误处理、文档、接口设计与命名、架构契合。
**交给工具**：格式化、import 排序、lint 违规、错别字。

## 四阶段流程

1. **摸上下文（2-3 分钟）**：读 PR 描述与关联工单；超 400 行先请拆分；看 CI 状态；理解业务需求。
2. **高层审（5-10 分钟）**：方案对路吗？有更简单的做法吗？与既有模式一致吗？能扩展吗？文件位置合理吗？测试策略对吗？
3. **逐行审（10-20 分钟）**：逐文件过四栏——正确性（边界、竞态、空值）、安全（注入、校验、敏感数据）、性能（N+1、无谓循环、阻塞）、可维护性（命名、单一职责、魔法数）。
4. **收口（2-3 分钟）**：总结关键关切 + 点名做得好的地方 + 给明确结论（批准 / 意见 / 需修改）；复杂的主动提出结对。

## 严重度标签（意见分级）

- 🔴 blocking：合并前必须改
- 🟡 important：应该改，有异议可讨论
- 🟢 nit：锦上添花，不阻塞
- 💡 suggestion：另路参考
- 🎉 praise：好活，当众夸

每个意见 = 标签 + 问题 + 建议修法；纯观点的注明「不阻塞」。

## 分歧与难点

- **分歧**：先复述对方理由确认理解；引规范/决策记录当裁判；裁判不了的升级第三人；一次说不服就标注存疑继续推进。
- **难开口的意见**：以问题形式起头（「这里的边界情况是想到了吗？」）；对事加建议；私下说人和人之间的话。

## 收尾自查

## 概述

**写技能就是把测试驱动开发套在流程文档上。**

你写测试用例（用子代理跑压力场景），看它失败（裸跑基线行为），写技能（文档），看测试通过（代理照做了），重构（堵漏洞）。

**核心原则：没亲眼看过代理没有技能时怎么失败，你就不知道这技能教的对不对。**

**前置要求：** 使用前必须理解「测试先行」技能——它定义红-绿-重构循环。本技能把 TDD 适配到文档上。

## 技能是什么

技能是**经过验证的技巧、模式或工具的参考指南**，帮未来的代理找到并应用有效方法。

**是：** 可复用的技巧、模式、工具、参考指南
**不是：** 「我有一次怎么解决了问题」的叙事

## TDD 映射

| TDD 概念 | 技能创作 |
|---|---|
| 测试用例 | 带子代理的压力场景 |
| 生产代码 | 技能文档（SKILL.md） |
| 测试失败（红） | 没有技能时代理违规（基线） |
| 测试通过（绿） | 有技能时代理照做 |
| 重构 | 堵住漏洞、保持合规 |
| 先写测试 | 写技能**前**跑基线场景 |
| 看它失败 | 逐字记录代理的借口 |
| 最小实现 | 只针对那些具体违规写技能 |
| 看它通过 | 验证代理现在合规 |
| 重构循环 | 发现新借口 → 堵 → 再验 |

## 什么时候建技能

**建：** 技巧不是凭直觉就会的；你会跨项目再用；模式广泛适用（不绑单个项目）；别人也受益。

**不建：** 一次性方案；别处已写透的标准做法；项目专属约定（写进项目说明）；机械约束（能用正则/校验强制的就自动化——文档留给判断题）。

## 技能类型与测法

| 类型 | 例子 | 测法 | 过关标准 |
|---|---|---|---|
| 纪律型 | TDD、完成前验证 | 学术问题（懂规则吗）+ 压力场景（顶着压力守吗）+ 叠加压力（时间+沉没成本+疲惫） | 最大压力下仍守规则 |
| 技巧型 | 条件等待、根因追踪 | 应用场景 + 变体场景 + 缺信息测试 | 能把技巧用到新场景 |
| 模式型 | 降复杂度、信息隐藏 | 识别场景 + 应用场景 + 反例 | 知道何时用、何时不该用 |
| 参考型 | API 文档、命令参考 | 检索场景 + 应用场景 + 缺口测试 | 找得到、用得对 |

## SKILL.md 结构

**Frontmatter（YAML，≤1024 字符）：** `name`（只许字母数字连字符）和 `description` 必填。

**description 只写「什么时候用」，不写「它做什么」——这条是血泪教训：** 测试发现，description 概括工作流时，代理会照着 description 干而**不读技能正文**。「任务间做一次代码审查」的 description 让代理真只审了一次，尽管正文流程图明确要审两次。改成只写触发条件后，代理正确读了流程图、跟了完整流程。

**这个坑：** 概括工作流的 description 是代理会抄的近道，正文沦为摆设。

```yaml
# ❌ 坏：概括工作流
description: 用于执行计划——每任务派子代理，任务间做代码审查
# ✅ 好：只写触发条件
description: 执行任务相互独立的实施计划时使用
```

**Keyword 覆盖：** 用代理会搜的词——错误消息原文、症状（flaky/hanging/竞态）、同义词（超时/挂起/冻结）、工具与文件类型。

**命名：** 动宾在前，说做什么或核心洞见：`条件等待` 好于 `异步测试助手`。

**token 效率：** 常驻每次对话的技能每个 token 都要命。常用技能 <200 词，其他 <500 词。细节移到工具 `--help`；重复的跨技能引用只留一句「必须用〈某技能〉做工作流」；代码内联 <50 行，重参考（100+ 行）拆独立文件。

**跨引用其他技能：** 只写技能名 + 明确要求标记（`**前置要求：** 必须理解〈某技能〉`）。不用 `@文件` 强加载语法——那会立刻烧掉大量上下文。

## 流程图使用纪律

**只用于：** 不明显的决策点；容易提前停的流程环；「A 还是 B」的选择。

**绝不用：** 参考材料（用表格/列表）；代码示例（用代码块）；线性指令（用编号列表）；无语义的标签（step1、helper2——标签必须有含义）。

## 代码示例

**一个出色的例子胜过一堆平庸的。** 选最相关语言；完整可跑、注释讲清「为什么」、来自真实场景、展示模式、拿来即改。**不做：** 5 种语言各来一遍；填空模板；生造的例子。

## 铁律

```
没有先失败的测试，就没有技能。
```

**新技能和改现有技能一律适用。** 不测就写的技能——删掉重来。不测就改的技能——同罪。

**无例外：** 「小补充」不例外；「就加一节」不例外；「文档更新」不例外；不留「仅供参考」的不测改动；不在跑测试时「顺手改」；删除就是删除。

**违反规则的字面 = 违反规则的精神。**（提前堵死整类「我按精神来的」借口。）

## 按失败形态选写法

写指南之前，先给基线失败分类。防住一类失败的形态，用在另一类上会** measurable 地帮倒忙**：

| 基线失败 | 对的形态 | 错的形态 |
|---|---|---|
| 压力下跳过/违反规则（懂但就是不做） | 禁令 + 借口表 + 红旗清单 | 软话（「建议…」「不妨…」） |
| 照做了但产物形状不对（提示词臃肿、结论埋没、复读规格） | **正面配方或契约**：直接说产物**是什么**——哪些部分、什么顺序 | 禁令清单（「别复述」「别叙述」） |
| 产物里漏了必备元素 | **结构化**：在模板里立必填槽位 | 模板旁边的散文提醒 |
| 行为本应取决于某条件 | 挂在可观察谓词上的**条件句**（「简报存在就引用它」） | 无条件规则 + 豁免从句 |

**为什么禁令在塑形问题上帮倒忙：** 有竞争激励时（「让提示词自包含」），代理会跟「别 X」讨价还价。头对头措辞测试里，禁令组产出的不要内容**明显更多**，甚至比无指导对照组还糟。配方没有讨价还价的余地：产物要么符合声明的形状，要么不符合。

**无论选哪种形态：** 不留余地从句——「别 X，除非要紧」重新打开谈判；附加一个 nuance 从句就能把稳定配方搅成噪音。真实的例外写成挂在可观察谓词上的独立条件句。豁免从句不设界——「此限制不适用于代码块」仍会压低代码块；必须豁免的部分，重构规则让它根本够不着。

## 堵理性化漏洞（纪律型技能）

聪明的代理在压力下会找漏洞。逐个显式堵：

**1. 堵每条具体退路。** 不只说规则，还要禁掉具体的绕法：

```markdown
先写代码后写测试？删掉。重来。

**无例外：**
- 不留作「参考」
- 不在写测试时「顺手改」
- 不看它
- 删除就是删除
```

**2. 建借口表。** 基线测试里代理的每个借口都进表：

```markdown
| 借口 | 现实 |
|---|---|
| 「太简单不用测」 | 简单代码也会坏。测试 30 秒。 |
| 「我回头补测试」 | 立刻过的测试什么也没证明。 |
| 「后补测试殊途同归」 | 后补 =「这代码干了什么？」先写 =「这代码**该**干什么？」 |
```

**3. 红旗清单：**

```markdown
## 红旗——停下，从头来

- 测试前写了代码
- 「我已经手动测过了」
- 「后补测试目的相同」
- 「重要的是精神不是仪式」
- 「这次不一样，因为…」

**中任何一条 = 删代码，用测试先行重来。**
```

## 微测措辞，再跑全场景

压力场景全跑又慢又贵。先用微测验措辞本身：

1. **每次调用一个全新上下文样本**：单发 API 调用或单发子代理。系统提示 = 指南将要生活的真实上下文（完整技能或提示词模板，不是孤立的指南）；用户消息 = 诱使失败的活儿。
2. **必须带无指导对照组。** 对照组不失败 = 没东西可修，停，别写指南。
3. **每变体 5+ 次。** 单样本会撒谎。
4. **人工读每条命中。** 可以程序打分，但模板复读和引用的反例会伪装成命中；只看自动计数会同时高估失败和成功。
5. **方差是指标。** 指南生效时，各次收敛到同一形状。五次五种理解 = 措辞没约束力——先收紧形态，别加字。

微测验措辞；纪律型技能的终审仍是压力场景。

## 反模式

- ❌ **叙事例子**：「2025-10-03 的会话里我们发现空 projectDir 导致…」——太具体，不可复用。
- ❌ **多语言稀释**：example-js.js、example-py.py、example-go.go——平庸 + 维护负担。
- ❌ **流程图里放代码**——不能复制粘贴，难读。
- ❌ **无义标签**：helper1、step3——标签要有语义。
- ❌ **批量造技能不逐个测**：写完一个必须停，走完部署检查清单才能碰下一个。不测的技能 = 不测的代码。

## 技能创作检查清单（TDD 版）

**红——先写失败的测试：**
- [ ] 造压力场景（纪律型 3+ 叠加压力）
- [ ] 无技能跑场景，逐字记录基线行为
- [ ] 从借口/失败里找模式

**绿——写最小技能：**
- [ ] name 只含字母数字连字符；frontmatter 有 name + description（≤1024 字符）
- [ ] description 只写触发条件、第三人称、带具体症状
- [ ] 全文布好搜索关键词（错误、症状、工具）
- [ ] 概述有核心原则；只针对基线失败写内容
- [ ] 写法形态匹配失败类型（查上表）
- [ ] 塑形类指南先微测（5+ 次、对照组、人工读命中）——纯参考技能免
- [ ] 一个出色例子（不多语言）
- [ ] 带技能重跑场景，验证合规

**重构——堵漏洞：**
- [ ] 收集新借口 → 加显式反驳 → 建借口表和红旗清单 → 重测到堵死

**质量：**
- [ ] 流程图只用于不明显决策；有速查表；有常见错误；零叙事；辅助文件只放工具或重参考

**部署：**
- [ ] 提交入库；广泛有用就考虑回馈上游 PR

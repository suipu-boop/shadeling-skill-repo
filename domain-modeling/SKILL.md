# 领域建模

设计的同时**主动**维护项目的领域模型：挑战含混术语、压测概念边界、结晶即落笔。只读词汇表不算本技能——那是谁都能做的一行习惯；改模型才是。

## 文件布局

```
项目根/
├── 词汇表.md          ← 全局术语
├── docs/decisions/    ← 决策记录（ADR）
│   ├── 0001-xxx.md
│   └── 0002-xxx.md
└── src/
```

多上下文大库：根放**词汇表地图**，各子目录自带词汇表与决策目录。**文件惰性创建**：第一条术语定下来才建词汇表，第一条决策要记才建决策目录。

## 会话中的五个动作

1. **对照挑战**：用户的用词与词汇表冲突时当场指出——「词汇表里〈X〉定义为 A，你刚才似乎指 B，是哪个？」
2. **磨尖模糊**：含混或一词多义时提出精确候选——「你说的〈账户〉，指客户还是登录账号？这是两个东西。」
3. **场景压测**：领域关系用具体场景压边界——编一个刁钻边界例子，逼出概念间的分界线。
4. **与代码互证**：用户陈述行为时对照代码；矛盾当场摆出来——「代码是整单取消，你刚说可以部分取消，哪个对？」
5. **当场更新**：术语一落定立刻写进词汇表，**不攒批**。词汇表里零实现细节——它是词汇表，不是规格、不是草稿纸。

## 决策记录（ADR）三条件

只有三条**同时**成立才提议记 ADR：

1. **难逆转**——日后改主意代价可观
2. **无上下文会费解**——未来读者会问「当时为什么这么干」
3. **真取舍**——存在真实的其他选项，为具体理由选了这边

缺任何一条都不记。记录本身同样当场落笔。

## 红线

- 词汇表条目 = 术语 + 定义 + 边界（不是什么）；不塞实现、不塞示例代码。
- ADR 记「决定 + 备选 + 理由」，不记讨论过程流水账。
- 用户否了某个方案且理由承重时才提议记 ADR，让未来的探索者不再重提。

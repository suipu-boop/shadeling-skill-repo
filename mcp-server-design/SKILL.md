# MCP 服务器设计四阶段

把一个外部服务封装成 MCP（Model Context Protocol）服务器，让大模型能稳定地调用它。质量标准只有一条：**模型拿着你的工具，能不能真正完成用户的现实任务。**

## 核心设计原则

**API 全覆盖 vs 工作流工具**
- 全覆盖（每个端点一个工具）：灵活、可组合，模型自由度高
- 工作流工具（一个工具封装一串操作）：对特定任务更省事、更少轮次
- 拿不准时优先全覆盖——模型会用基础工具自己组合出工作流

**工具命名**
- 动词式、可读、前缀一致：`github_create_issue` / `github_list_repos`
- 名字即文档：模型靠名字+描述决定调不调，别起 `do_stuff`

**上下文管理**
- 工具描述精炼；返回数据聚焦、支持过滤/分页
- 别让一次调用返回 10 屏无关数据，挤占模型上下文

**错误信息可行动**
- 报错要告诉模型「下一步怎么办」，不是甩异常栈
- 例：`日期格式应为 YYYY-MM-DD，你传了 2026/10/1`优于 `ValueError`

## 四阶段流程

### 阶段一：研究规划
1. 吃透目标服务的 API 文档：端点、鉴权、数据模型、限流
2. 定工具清单：从最常用操作开始，覆盖优先
3. 定传输方式：本地进程用 stdio；远程服务用流式 HTTP（无状态 JSON 更好维护）

### 阶段二：实现
每个工具五件事：
- **输入 schema**：字段带约束、描述、示例
- **输出 schema**：能结构化就结构化（`outputSchema` / `structuredContent`），客户端好处理
- **描述**：功能一句话 + 每个参数说明 + 返回什么
- **实现**：I/O 用异步；错误处理带可行动信息；支持分页
- **注解（annotations）**：`readOnlyHint` / `destructiveHint` / `idempotentHint` / `openWorldHint`，如实标注——调用方据此做权限控制

基础设施三件套：带鉴权的 API 客户端、统一错误处理、JSON/Markdown 双格式响应。

### 阶段三：评审与测试
- 代码：无重复、错误处理一致、类型覆盖完整、工具描述清晰
- 构建：语法编译通过
- 实测：用 MCP Inspector 打开服务器，逐工具调用验证正常路径与报错路径

### 阶段四：评测
写 10 道评测题，测「模型用这套工具能否答对复杂现实问题」：

| 要求 | 含义 |
|---|---|
| 独立 | 每题不依赖其他题的上下文 |
| 只读 | 只需非破坏性操作即可作答 |
| 复合 | 一题需要多次工具调用、深入探索 |
| 真实 | 是人类真的会问的问题 |
| 可验证 | 有唯一、明确的答案，可字符串比对 |
| 稳定 | 答案不随时间漂移 |

出题流程：列工具清单 → 用只读操作探数据 → 出 10 题 → **自己先做一遍**验证答案 → 存为 XML（`<qa_pair><question>…</question><answer>…</answer></qa_pair>`）。

## 验收清单

- [ ] 工具名动词式、前缀统一
- [ ] 每个工具有输入 schema（含约束与示例）+ 尽量有输出 schema
- [ ] 错误信息可行动（告诉模型怎么改）
- [ ] 注解如实（只读/破坏性/幂等）
- [ ] Inspector 实测通过
- [ ] 10 道评测题自己先验过答案

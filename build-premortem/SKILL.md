# 立项预审

预审的目的**不是劝退，是找全项目最脆的那根假设**，然后设计最小的验证动作——假设验证了再扩大投入，验证不了省下整个工期。

## 什么时候预审

要动手做：新产品/MVP/落地页/SaaS/内部工具/agent 工作流/大功能。**跳过条件**：小实现修复、重构、依赖升级、已验证且验收明确的小改动——这些直接做。

## 七风险清单（逐项过）

| 风险 | 一句话追问 |
|---|---|
| 需求 | 有证据表明特定用户**急**要吗？（还是「应该有人需要」） |
| 定位 | 目标用户一句话能听懂它是什么、为什么重要吗？ |
| 变现 | 有可信的付费路径吗（谁掏钱、为什么掏）？ |
| 留存 | 用户第一次用完，**第二次为什么回来**？ |
| 信任 | 需要用户交出数据/改变习惯/依赖集成——他们凭什么信？ |
| 分发 | 有可重复的触达方式吗（还是「发朋友圈看看」）？ |
| 采纳 | （功能类）这功能会改变用户行为，还是只多块界面？ |

## 五段输出（短而决策导向）

1. **风险判定**：低/中/高 + 一句话理由。
2. **最大假设**：最可能弄死项目的那一个（只挑一个）。
3. **先找的证据**：动工前能拿到的最小有效信号。
4. **下一步**：一个具体验证动作，或缩小后的首版范围。
5. **暂缓清单**：明确现在**不**做什么。

## 纪律

- 对证据薄弱直说，但不贬低想法本身——预审是工程不是评审表演。
- **产品风险与工程难度分开报**：做得出 ≠ 卖得动，两者混淆是最常见的误判。
- 事实缺失就点名缺什么证据，**不编造市场论断**。
- 已验证的想法：指出让它低风险的证据，建议最小实现切片。

## 收尾清单

七风险逐项过 / 最大假设唯一 / 验证步最小化 / 暂缓清单明确 / 产品风险与工程难度分列 / 无编造论据。

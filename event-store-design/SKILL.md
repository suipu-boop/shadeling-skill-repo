# 事件存储设计

事件存储是事件溯源系统的地基：**只追加的事实日志**，按流组织、全局有序。

## 流模型

- 存储按**流（stream）**分区，一个聚合一条流：`Order-3f2a…`（聚合类型+唯一 ID）。
- 流内事件按版本号排（1、2、3…），全局另有单调递增位置（消费进度用它）。
- 重建聚合状态 = 从头重放该流事件；跨流查询走投影（见读写分离与投影模式技能）。

## 五项硬要求

| 要求 | 说明 |
|---|---|
| 只追加 | 事件不可变，永不 UPDATE/DELETE——它们是已发生的事实 |
| 有序 | 流内严格有序；并发写同一流要能检测冲突 |
| 版本化并发 | 乐观锁：写入时带期望版本，不匹配即拒绝（防并发覆盖） |
| 可订阅 | 新事件实时可通知（投影/集成靠它） |
| 幂等 | 事件 ID 去重，重复投递/重放不产生副作用 |

## 选型速查

- **已有 PostgreSQL**：直接用 Postgres 建事件表（流 ID + 版本 + 数据 + 元数据），唯一约束实现乐观锁——最省运维，自建主流路线。
- **专用事件库（EventStoreDB 类）**：订阅、投影、竞态控制开箱即用，代价是引入单职组件。
- **消息队列（Kafka 类）**：高吞吐管道强项，但按流回查/精确定位弱，适合做分发层而非唯一事实源。
- 云托管键值（DynamoDB 类）：无运维，查询能力受限。

## 设计要点

- **事件 ID 幂等去重**：写侧生成唯一事件 ID，存储层唯一索引兜底——重试/重放安全。
- **第一天就版本化事件**：加 version 字段；schema 演化靠升级转换，不改已写事件。
- **元数据带上因果链**：correlation_id（本次业务全程）+ causation_id（哪个事件/命令引发了我）——排障时事件链路一查到底。
- **按查询模式建索引**：全局位置扫投影用，流内版本查聚合用；别为「以后可能」过度建。
- **快照缓解重放成本**：事件数太多的流定期存快照，重放从快照起步——是优化不是必需，先裸跑。

## 常见坑

- 把事件存储当普通表用（更新/删除事件）——事实源被污染，全线失真
- 无乐观锁——并发写同流静默丢事件
- 无幂等键——投递系统一重试就重复副作用
- 事件不带元数据——出事查不出因果链

## 收尾清单

append-only 有纪律 / 流命名含聚合类型 / 乐观并发在存储层 / 事件 ID 幂等 / 因果 ID 全链 / 事件版本化起点就有。

# 订阅计费

计费系统三支柱：**状态机正确、失败挽回自动化、变更折算无争议**——算错钱是信任崩塌型事故。

## 订阅状态机（转换必有明确触发与副作用）

```
trial（试用）→ active（生效）→ past_due（逾期）→ canceled（取消）
                    ↑______paused（暂停）______|
```

- **past_due ≠ canceled**：扣款失败进逾期态（挽回窗口开着），别急着取消——挽回序列跑完（见下）才走取消。取消要明确触发条件（挽回 N 天无效）。
- 暂停/恢复是独立转换（挂起保留数据，恢复重启计费锚点）——别用「取消再重开」模拟，锚点丢了按天折算就乱。
- **计费锚点**（billing anchor）：周期起点定死后所有折算以它为基准——升级降级改周期都以锚点推算剩余天数。

## 催缴挽回（dunning）

扣款失败的标准挽回序列（按天）：

1. **智能重试**：第 1/3/5/7 天重试（重试时点优选发薪日/卡账单日附近，而不是无脑连打——每次失败刷拒付率）。
2. **提醒客户**：每次失败即触发换卡通知（直达更新入口）——多数失败只是卡过期，一条消息救回大半。
3. **宽限期**：服务不断（3-7 天），停服前 48h 再次警告——停服是最后手段且必须可预期。
4. 降级不停用：挽回失败先降级到免费档（保留账号与数据）——全删是把回头客变成流失客。
5. **挽回漏斗复盘**：哪一步挽回最多、哪步流失——序列本身要迭代。

## 按比例折算（proration）

周期中变更（升级/降级/加席位/换周期）的折算规则**先定死再上线**：

- 升级：剩余周期补差价（当天生效）。
- 降级：差价转余额/下次抵扣（行业惯例，减少争议）——退款流程复杂且可被滥用。
- 折算基准 =（剩余天数 / 周期总天数）× 价差，按天算，时区边界全系统统一。
- 每笔折算明细进账单行项——**客户看得懂的账单才不会变成客服工单**。

## 口径三统一

年费摊月方式统一（合同价/12 还是实付月数，财务与数据必须同口径）、时区统一（UTC 存储展示本地化）、取消即期 vs 期末生效统一（全站一种）。
